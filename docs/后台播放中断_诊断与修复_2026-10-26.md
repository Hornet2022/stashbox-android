# 后台播放中断：诊断与修复（2026-10-26）

> 触发：内测用户反馈「**听匣 app 放后台播放时，播放几分钟后就没声了**」。
> 本文只写**查证过的**机制与**可复核**的证据，推测一律标注为「未排除」。

---

## 一、现象

- 内测用户：App 切到后台播放，**几分钟**后声音停住。
- 再次打开 App：进度停在断点，界面显示播放失败（若曾回到前台）。

---

## 二、先说结论（一句话）

**一条瞬时的断流 = 永久停止。**

断流本身是网络世界的常态（息屏、省电策略、网络切换都会掐断长连接）；
真正把「抖一下」变成「停死了」的是客户端的处理：
**出错后没有任何自动恢复**，唯一的恢复入口是用户手动点「重试」，
而后台播放时**没有人点**。

---

## 三、机制（逐条可复核）

### 3.1 音频播放全程依赖一条长连接

| 环节 | 位置 | 事实 |
|---|---|---|
| 播放器 | `PlayerModule.provideExoPlayer` | `DefaultMediaSourceFactory(cacheFactory)`，上游走缓存 |
| 缓存 | `OfflineDownloadManager.buildCacheDataSourceFactory` | `CacheDataSource` → `FallbackHttpDataSource` → `DefaultHttpDataSource` |
| 缓冲 | media3 `DefaultLoadControl` | 只维持播放位置**前方约 50s** 的缓冲 |

⇒ 上游那条 HTTP 连接要在**整篇播放期间**一直开着：
不是「开头下完就没事了」。

### 3.2 断流 → 播放器报错 → 状态 IDLE

- `FallbackHttpDataSource.read()`：中途读失败 ⇒ 标记主地址失败 ⇒ 抛 `HttpDataSourceException`。
- media3 `ExoPlayerImpl.stopInternal(error)` ⇒ `copyWithPlaybackState(STATE_IDLE)` + 记下错误。

### 3.3 ⭐ 客户端此前**没有任何自动恢复**

`PlayerController.onPlayerError` 原来只做一件事：`notifyPlaybackError(...)`
⇒ 状态置 `ERROR`、弹一句文案、**等用户手动点重试**。

而 `retry()` 是 App 内**唯一**的恢复入口 —— 后台没人点 ⇒ 永久停止。

### 3.4 ⭐ 而且出错那一刻**当场失去前台服务保护**

media3 1.4.1 源码（`MediaNotificationManager.shouldRunInForeground`）：

```java
return controller != null
    && (controller.getPlayWhenReady() || startInForegroundWhenPaused)
    && (controller.getPlaybackState() == Player.STATE_READY
        || controller.getPlaybackState() == Player.STATE_BUFFERING);
```

`READY / BUFFERING` 之外 ⇒ `maybeStopForegroundService()` ⇒ 服务退出前台。

⇒ 出错的那一刻，App 从「有前台服务保护」变成「普通后台服务」：
Android 8+ 的后台服务限制只再给**几分钟**，厂商的省电策略更是随时能杀。

### 3.5 手动点「重试」还会**从头开始**

`retry()` 原来不传 `resumePositionMs` ⇒ `play()` 取默认 0 ⇒ 播放器从头播。
用户听了 3 分钟，点一下重试，**前 3 分钟白听**。

### 3.6 早写好、却从没被用上的那条自愈路

`FallbackHttpDataSource` 的 KDoc 明写着：

> 中途断流：标记主地址失败。**下一次 open（播放器重试）就会走备用地址**，
> 而缓存里已经下好的部分仍在 → 从断点续播。

问题是：**此前没有任何代码路径会再次 `open`**（除非用户手动点重试）。
⇒ 设计好的自愈机制，事实上从未生效。

## 四、「几分钟」的三处吻合

1. **仓内自带的实测记录**（`OfflineDownloadManager` 的 KDoc，2026-10-22）：
   > 实测音频下到 **57%** 就断（`position=172s, state=ERROR, Source error`）

   172 秒 ≈ **3 分钟**，与用户描述的「几分钟」一致。
2. **Android 后台服务限制**：掉出前台后，普通 started service 只被允许再跑几分钟。
3. **media3 的加载重试**：`DefaultLoadErrorHandlingPolicy.getRetryDelayMsFor`
   返回 `min((errorCount-1)*1000, 5000)` —— 会自动重试，但**连续失败耗尽后**
   就落到 `STATE_ERROR`，交回 App 处理（而 App 不处理）。

---

## 五、为什么是「后台」而不是前台

| | 前台播放 | 后台播放 |
|---|---|---|
| 断流本身 | 一样会断 | **更容易断**：息屏 → Doze / 厂商省电策略；wifi↔移动网络切换；后台联网限制 |
| 断流后的表现 | 停在失败界面，用户**看得见、能点重试** | 没人点 ⇒ 永久停止 |

⚠️ **关键区分**：前台服务（`foregroundServiceType="mediaPlayback"`）覆盖的是
**进程保活**与（配合 `setWakeMode`）**CPU 唤醒**；
它**不覆盖厂商层面的「后台联网限制」**（MIUI 等会限制后台 App 的网络）。

⇒ 所以「前台服务已在、却还是断了」是可能的，不是矛盾。

| # | 改动 | 位置 |
|---|---|---|
| 1 | **失败分类**：瞬时网络类 vs 内容类 | 新增 `audio/PlaybackFailure.kt` |
| 2 | **自动重连**：网络类错误自动 `prepare()` 重开数据源，**从断点续上**，带退避与次数上限 | `PlayerController` |
| 3 | **恢复期是独立状态** `RECOVERING`，界面显示「正在重连」并允许暂停 | `PlayerController` + 3 处 UI |
| 4 | **手动重试保留位置** | `PlayerController.retry()` |

| 6 | **用户不打算听时，不拿失败去打扰他**：暂停/停止之后才到的加载失败回调**只记日志**，不改状态、不弹错误、不自动重连 | `PlayerController.onPlayerError` |
| 7 | **可观测**：`playback_error` / `playback_recovered` 两条埋点 | 安卓 `EventNames` + 后端 `EventName` |

### 6.0 两条容易写错的边界（实现时踩到并修掉的）

**① media3 出错时不会重置 `playWhenReady`** —— 它是「用户此刻是不是还想听」的可靠判据：

- 用户按了暂停 → `playWhenReady=false`；
- 而**上一次 `prepare()` 的加载失败回调常常在这之后才到**；
- 若不判这一条，自动恢复照样启动 ⇒ **用户明明按了暂停，音频却又自己放了起来**。

⇒ 所以自动恢复的入口与失败处理都先判 `playWhenReady`：
不在播 ⇒ 这次失败与用户无关（只记日志）。

**② 恢复期不能靠状态变量判断** —— 状态会被播放器的回调改写
（恢复期里播放器可能短暂处于「就绪但没在播」，把状态改成 `PAUSED`）。
⇒ 内部逻辑用独立的 `recovering` 标志，状态只负责给界面看。

### 6.1 为什么 `player.prepare()` 就够（依据 media3 1.4.1 源码）

`ExoPlayerImplInternal.prepareInternal()`：

```java
resetInternal(
    /* resetRenderers= */ false,
    /* resetPosition= */ false,          // ← 位置保留
    /* releaseMediaSourceList= */ false,  // ← 媒体源保留
    /* resetError= */ true);
```

⇒ **位置保留、媒体源保留**，只是把数据源重新打开一次；
而 `CacheDataSource` 会先命中本地缓存、只对缺的那一段发 Range 请求
⇒ **「从断点续播」是白送的**。

顺带：`FallbackHttpDataSource` 那条「下一次 open 走备用地址」的路，
现在**终于有了下一次 open**。

### 6.2 为什么不用 `player.retry()`

media3 1.4.1 的 `ExoPlayer` 接口**没有** `retry()`（那是 ExoPlayer2 时代的 API）。
可用的等价物就是 `prepare()`（语义见上）。

## 七、真机验收清单（**分钟级** —— 这是上一轮的缺口）

> 上一轮的后台播放验证只做了 **25 秒**（见 `audio-app-capabilities.md`），
> 而故障发生在**几分钟**量级 ⇒ 验证窗口本身就短于故障周期。
> **这次的验收窗口必须超过故障周期。**

| # | 步骤 | 期望 |
|---|---|---|
| 1 | 播放 → 切后台 → **静置 10 分钟**（中途不碰屏幕） | 声音**不断**；`dumpsys media_session` 里 position 持续增长 |
| 2 | 播放 → **息屏** → 静置 10 分钟 | 同上 |
| 3 | 播放 → 切后台 → **开飞行模式 30 秒再关** | 声音**自动接上**（可能有几秒卡顿），位置**不丢** |
| 4 | 同上，但**一直**开飞行模式 | 最多重试 5 次（约 30 秒）后显示失败提示，**不再无限重试** |
| 5 | 播放到 3 分钟 → 手动断网 → 恢复网络 | 从**断点**继续，不是从头 |
| 6 | 前台播放 → 断网 → 点「重试」 | 从**断点**继续（不是从头） |

### 7.1 抓证据的命令

```bash
# 播放中断时发生了什么（客户端日志）
adb logcat -s PlayerController:* ExoPlayerImpl:* EventLogger:* | grep -iE "auto recovery|playback interrupted|playback error"

# 进程是否还活着 / 服务是否在前台
adb shell dumpsys activity services com.tingxia.audio | grep -E "AudioPlayerService|isForeground|startForegroundCount"

# 服务端侧：这次断流的痕迹（2026-10-26 新增埋点）
SELECT type, metadata, created_at FROM feedback
 WHERE type IN ('playback_error','playback_recovered')
 ORDER BY created_at DESC LIMIT 50;
```

## 八、仍未排除的部分（不装作已经解决）

**具体是「谁」掐断了那条连接，目前只有推断，没有直接证据。**

三个候选（客户端看到的都是同一个 `IOException`，无法直接区分）：

1. **厂商后台管控**（MIUI 等的省电策略 / 后台联网限制）—— 最可能；
2. **Doze**（息屏后系统挂起网络）—— 需要核实前台服务是否真的豁免；
3. **服务端或中间设备断长连接**（nginx / OSS / 运营商 NAT 的空闲超时）。

⇒ 靠新埋点区分：`playback_error` 的 `cause`（异常类名）、`position_ms`
（断在第几分钟）、`kind`。再结合测试员机型，就能定位到具体那一个。

**同时要做的运营动作**（不靠代码解决的那一半）：
请测试员在手机上开启「**自启动**」与「**省电策略 → 无限制**」，
并允许「后台联网」—— 这类引导在国内安卓上是标配。
