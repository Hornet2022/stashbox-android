# 复盘：播放中断提示「网络不稳，正在重连…」（2026-11-09）

> 一句话：**网络确实没问题**，是服务端对客户端缓存的**旧音频地址**返回了 404，
> 而客户端把这个 404 翻译成了「网络不稳」。
>
> 而且这次故障是**我们自己造成的**：18:46 做端到端验证时重跑了一篇文章的蒸馏，
> 音频重新生成 ⇒ 内容寻址 key 变 ⇒ 旧文件被删 ⇒ 正在听的用户手里的 URL 失效了。

---

## 1. 用户看到的

内测反馈：听的过程中弹出「**网络不稳，正在重连…**」（附「重试」按钮），
并明确表示「**手机网络正常**」。

用户是对的。

---

## 2. 证据链（时间戳严丝合缝）

| 时间 | 证据 | 说明 |
|---|---|---|
| 18:46 | 磁盘上只有 `art_3dd88aca….50967cd2.mp3` | 音频在 18:46 被**重新生成**（我做的端到端验证） |
| — | DB `distilled_articles.audio_url` = `…50967cd2.mp3` | 服务端说的"当前音频"是新版 |
| 19:27:22 | 网关 `GET /audio/audio/art_3dd88aca….4c67fadb.mp3` → **404** | 客户端用的是**旧 key** |
| 19:30:45.317 | 网关同上 → **404** | 距离下一条 27ms |
| 19:30:45.290 | 客户端埋点 `playback_error` | `kind=transient_network`, `position_ms=127628`, `duration_ms=342480`（= 5:42，与截图总时长一致） |
| 19:31:44 / 19:32:41 | 同样的 404 | 自动重连一轮打一次 |

⇒ **服务端 404 与客户端报错只差 27ms** —— 就是同一次失败。

`position_ms=127628`（2:07）是失败时的播放位置；截图里显示 4:03，
是因为客户端用**缓存里已下载的部分**继续播了一会儿，缓存用完才彻底断。

### 为什么客户端拿着旧 URL

- 客户端把 `audio_url` 缓存在本地 Room；
- 列表页只在 `audioUrl` **为空**时才回服务器补 ⇒ **一旦缓存就不再刷新**；
- 而服务端换 key 后没有让旧 URL 失效的过渡期 ⇒ 旧 URL 直接 404。

### 为什么"网络不稳"是假话

客户端的失败分类（`PlaybackFailure.classify`）本来是**对**的：
404 属内容类、不该自动重连。但链路是：

```
主地址 → 404（服务端明确说了"文件没了"）
        ↓ 客户端换备用地址
备用地址 → 连接超时
        ↓ 最终抛出的异常是「超时」
分类器只看到「超时」⇒ 判成"瞬时网络类"
⇒ 界面显示「网络不稳，正在重连…」
⇒ 并对一个永远不存在的文件反复重连
```

⇒ **备用地址的失败把主地址的真实状态掩盖了。**

## 3. 三个"本该早发现"的坑

1. 🔴 **生产埋点里 `cause` 是 `"y"`**。
   上报的是 `cause.javaClass.simpleName`，而 release 包开了 R8 ⇒ **类名被混淆**。
   debug 包不混淆 ⇒ 本地一切正常 ⇒ 这个坑在开发期**完全看不见**。
   （2026-10-26 那两条埋点显示 `SocketException`，是因为那是平台类，不被混淆。）
2. 🔴 **nginx 的 API 访问日志文件被删了，但 nginx 仍持着旧 fd** ⇒
   `/var/log/nginx/stashbox.access.log` 不存在，API 流量写进了黑洞。
   排查时只能靠网关的 structlog 才找到那几条 404。
3. ⚠️ **内容寻址 key 的代价被低估了**。
   key 带内容 hash 是为了解决 2026-10-21 的"客户端播旧音频"（见
   `app/services/storage/base.py::versioned_audio_key`），
   但它同时带来"**旧 URL 硬失效**"——这一面当时没有对策。

## 4. 治本

### 4.1 服务端：过期 key 302 重定向到当前版本（**已上线，已装用户立刻恢复**）

网关的音频静态目录改成 `AudioFilesWithStaleRedirect`（继承 `StaticFiles`）：

```
请求的文件不存在
  → 查该文章**当前**的音频 key（DB：蒸馏行优先，主档兜底）
  → 与请求的不同 ⇒ 302 重定向过去
```

- 旧 URL 永远拿得到**当前**音频：既不 404，也不会播到旧音频；
- 已装的旧客户端**不用发版**就能恢复；
- 继承 `StaticFiles` 是为了**保留 Range 续传**（客户端实测在用 206）。

证据（生产）：

```
GET /audio/audio/art_3dd88aca….4c67fadb.mp3
  → HTTP 302 → /audio/audio/art_3dd88aca….50967cd2.mp3
  → 跟随后 HTTP 200，2,797,101 字节，audio/mpeg
Range 跟随重定向 → HTTP 206（续传能力保留）
不存在的文章 → 仍 404（不乱重定向）
```

### 4.2 客户端（0.5.3 / versionCode 26）

1. **备用地址的失败挂上主地址的失败**（`addSuppressed`），
   分类与文案都看**整条链（含 suppressed）** ⇒ 404 被如实判成内容类，不再无限重连。
2. **文案不再说假话**：404 → 「音频已更新或已失效，请重新进入文章」；
   503 → 「服务暂不可用」；只有真的超时才说「网络不给力」。
3. **埋点的 `cause` 改用固定字符串**（`http_404` / `socket_timeout` / `io_error` …），
   不再依赖会被混淆的类名；另加 `http_status` 字段。
   R8 规则里额外保留异常类名作补充信息。

## 5. 流程上的教训（这次是我踩的）

**端到端验证不要重跑"已有文章的蒸馏"。**

18:46 我为了验证端到端链路，重跑了 `art_3dd88aca…` 的蒸馏 ⇒
音频重新生成 ⇒ key 变 ⇒ 旧文件被删 ⇒ **正在听这篇的内测用户当场断流**。

⇒ 端到端验证应该用**新文章**（新 id），不要碰已被真人使用的文章。
⇒ 若必须重跑，先确认"这篇文章当前没有人在听"。
