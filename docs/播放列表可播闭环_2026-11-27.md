> 状态：**已实现；客户端 0.5.6 已发布**（生产 `/var/www/stashbox-downloads/tingxia-0.5.6.apk`，
> `versionCode=29` / `versionName=0.5.6`，已核对与本仓源码同版本）。
> 本文是「缝合定义」——判据、文案、落点都写在这里，也写进代码。
> **任何一方想改数字或文案，先改这里，再改代码**，别各自发明。

## 0. 一句话

**「蒸馏完了但播放列表还是说没有音频」不是服务端坏了，是两处客户端没接上：
① 失败文案没走既有的「还没好」判据；② 蒸馏完成时没人把音频地址写回播放列表快照。**

## 1. 现象与证据（生产日志，2026-11-26）

用户端（0.5.5，已核实**含** ad7e192 修复：外网 APK sha256 = 本地构建 sha256 = `eed4c74b…`，
mapping 内含 `access$backfillMissingMetadata`）在播放列表点已剪藏的文章：

| 时刻 | 文章 | 文章创建于 | `GET /articles/{id}/audio-url` | 结果 |
|---|---|---|---|---|
| 11-26 07:22:40 | `art_30fb7dca…` | 07:20:50（2 分钟前） | **404** | 蒸馏中 → 语义正确 |
| 11-26 07:22:41 | `art_a7ebe143…` | 07:21:35（1 分钟前） | **404** | 蒸馏中 → 语义正确 |
| 11-26 07:23:07 | 同上两篇再点 | | **404** | 蒸馏中 |
| 11-26 07:28:12 | 三篇全试 | 已完成 | **200** | 能播（用户**手动再点了一次**） |

蒸馏全程约 4 分钟（LLM 改写 ~50s + TTS ~150s+）。
⇒ 404 **不是缺陷**（服务端语义正确），**缺陷是"好了以后没人告诉客户端"**：
用户必须自己再点一次才知道能播。

## 2. 拆解：三个环节各自的状态

| 环节 | 现状 | 判定 |
|---|---|---|
| ① 服务端 `audio-url` | 未就绪 → 404 + `code 40400`（"还没好"） | ✅ 正确，**不改** |
| ② 客户端播放失败文案 | 播放列表自己写了笼统的「这一篇还没有音频，蒸馏好了才能播」 | ❌ **缺陷 1** |
| ③ 蒸馏完成 → 播放列表快照 | `DistillReadyWorker` 拿到 ready 时**手里已有 `article.audioUrl`**，却只拿去发通知，**没写回播放列表快照** | ❌ **缺陷 2** |

**为什么缺陷 2 存在**：`backfillMissingMetadata` 只在**本机列表数据变化**时触发
（Room emit），而"服务端蒸馏完成"**不写本机 Room 表** ⇒ observer 不 emit ⇒ 不触发补齐。
⇒ 播放列表那条永远是空快照 ⇒ 用户点了才发现。

## 3. 契约

### C1（既有，不改）：`audio-url` 未就绪 = 404 + code 40400

`ApiEnvelope.isAudioNotReady`（`httpCode == 404 && bizCode == 40400`）就是
"还没好"的**唯一判据**。服务端语义与它对齐，**本轮不动服务端契约**。

### C2（缺陷 1）：播放列表的播放失败必须走既有的分级文案

* 落点：`PlaylistViewModel.playFrom`（以及 `backfillMissingMetadata` 的失败分支）。
* 判据：既有 `friendlyError(ex, fallback)` → 内部走 `apiEx.isAudioNotReady`。
* 文案：未就绪 ⇒ **「音频还在蒸馏中，请稍候」**（既有文案，`ErrorMessages.kt:87`）；
  真失败/真缺失 ⇒ 兜底文案。
* ⚠️ **不许**在播放列表里另写一句笼统的"没有音频"—— 那正是缺陷 1 本身。

### C3（缺陷 2）：蒸馏完成时必须把地址写回播放列表快照

* 落点：`DistillReadyWorker.doWork()` 的 `READY / LISTENED` 分支。
* 数据源：**它已经拿到的 `article.audioUrl` / `article.durationSec`**
  （`articleRepository.getArticle(articleId)` 返回完整 `Article`）⇒ **零新增请求**。
* 写入：`PlaylistRepository.contains(articleId)` 为真 ⇒ `refreshUrl(articleId, audioUrl, title, durationSec)`；
  不在列表里 ⇒ **不写**（不制造幽灵条目）。
* 时机：与既有本地通知同一点 ⇒ 用户收到"文章已就绪"通知时，播放列表**同时**已是可播态。

### C4（明确不做）：服务端推送

* 理由（既有事实，见 `DistillNotifier` 的类注释）：全仓**无任何推送通道代码**
  （APNs/FCM/个推/极光零命中），`push_notifications` 表 0 行 ⇒ 接入推送要先有
  厂商通道与设备凭据（要用户账号授权的事）。
* 而 C3 落地后，"文章好了"这件事**已经**通过既有 `DistillReadyWorker` +
  本地通知（刻意无声，避免抢音频焦点）到达用户 ⇒ **推送不是闭环的必要条件**。
* ⇒ 记入「被否证的做法」：**不要**为了这个闭环去引入推送通道。

## 4. 守卫（红测试 + 变异）

| 守卫 | 断言 | 变异（必须变红） |
|---|---|---|
| `PlaylistSnapshotSyncTest`（新） | 就绪且该文在播放列表 ⇒ **写回**，且参数含 `article.audioUrl` / `durationSec` / `title` | 删掉写回 ⇒ 红 |
| 同上 | 就绪但**不在**播放列表 ⇒ **不**写回（不许造幽灵条目） | 无条件写回 ⇒ 红 |
| 同上 | 地址为 null / 空白 ⇒ **不**写回（写了也等于没写） | 空地址也写 ⇒ 红 |
| `PlaylistViewModelTest`（补） | audio-url 返 404+40400 ⇒ 文案说「还在蒸馏」，**不是**"没有音频" | 改回笼统文案 ⇒ 红 |
| 同上 | status=**failed** ⇒ 文案说「没能生成」并给出下一步 | 失败也说"还在蒸馏" ⇒ 红 |

**为什么守卫落在 `PlaylistSnapshotSync` 而不是 `DistillReadyWorker`**：
Worker 需要 Android `Context` 与 `WorkerParameters`，单测要 Robolectric + work-testing，重且脆；
而这段逻辑最容易错的恰恰是「什么时候该写、什么时候不该写」⇒ 抽成**不依赖 Android** 的
`PlaylistSnapshotSync` 纯逻辑单元，用普通 JUnit 测（`PlaylistSnapshotSyncTest`，6 例）。

⚠️ **已知守卫缺口（如实标注，别当成已覆盖）**：「failed 分支不写回」目前由
`DistillReadyWorker.doWork()` 的**分支结构**保证（只有 READY / LISTENED 分支调
`syncPlaylistSnapshot`），**没有**独立断言钉住它 ⇒ 将来有人把调用挪到失败分支，
现有守卫不会红。要补的话应给 Worker 加一条结构断言。

⚠️ 假绿陷阱（已在测试里钉住）：`RecordingArticleApi` 必须抛**真实形态**
`ApiException(http=404, biz=40400)` —— 早先抛 `IllegalStateException` ⇒ 走不到分级分支
⇒ 文案分级守卫会**假绿**。

## 5. 验收

* 自动：安卓端全量测试零回归 + 上面 4 条守卫绿。
* 活体（用户侧，一次剪藏即可）：
  1. 剪藏一篇 → **立刻**加进播放列表；
  2. 蒸馏完成（≈4 分钟）后**不点任何东西**，打开播放列表 ⇒ 该条应显示时长、可播；
  3. 点它 ⇒ 直接播（无需先点一次报错）。

## 6. 被否证的做法（留档，别再做）

| 做法 | 否证证据 |
|---|---|
| 「服务端给未就绪的 audio-url 返 200 + status」 | 客户端已有 `404 + 40400` 判据且既有分级文案 ⇒ 改服务端契约属无收益的破坏性变更 |
| 「引入 FCM/厂商推送做闭环」 | 无通道无凭据；C3 已覆盖"好了"的到达 |
| 「把轮询拉长 / 详情页常驻轮询」 | 进程被回收就没了；`DistillReadyWorker` 已用 WorkManager 解决跨进程存活 |
| 「靠 `backfillMissingMetadata` 自动补齐」 | 它只在 Room emit 时跑，服务端完成不写本机表 ⇒ 不触发（缺陷 2 的根因） |
